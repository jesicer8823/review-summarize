# Shopkeeper Brain 项目总结报告

## 概述

本项目是一个面向商品资料、说明书、技术文档的 RAG 知识库问答系统。核心目标是将 PDF、Markdown、Word 等非结构化资料导入知识库，并在用户查询时通过商品名确认、多路召回、排序融合和大模型生成，给出基于资料的问答结果。

项目的主要后端逻辑集中在 `knowledge/` 目录下，整体分为两条业务链路：

- 知识入库链路：文件上传、文档解析、图片处理、文档切分、商品名识别、向量化、Milvus 入库、Neo4j 图谱构建。
- 查询问答链路：商品名确认、问题重写、多路检索、RRF 融合、Rerank 精排、答案生成、会话历史记录。

系统不是单一向量检索方案，而是将向量检索、HyDE 检索、知识图谱检索和外部 Web/MCP 检索组合起来，形成一个混合检索增强问答流程。

## 技术架构

### 后端框架

- `FastAPI`：提供导入接口、查询接口、任务状态接口、历史记录接口和 SSE 流式输出。
- `Uvicorn`：作为 FastAPI 服务运行入口。
- `LangGraph`：负责导入流程和查询流程的状态图编排，支持条件分支、多路并行和节点汇合。
- `LangChain`：作为能力层使用，主要提供 `ChatOpenAI`、消息结构、文本切分器等组件。

### 数据库与中间件

- `Milvus`：核心向量数据库，存储文档 chunk、商品名、实体名的混合向量，用于向量检索、商品名对齐和实体对齐。
- `Neo4j`：图数据库，存储从 chunk 中抽取的实体、关系和 chunk 关联，用于知识图谱检索。
- `MongoDB`：存储会话历史，包括用户问题、助手回答、重写查询和商品名信息。
- `MinIO`：对象存储，用于保存原始上传文件和文档图片资源。
- `SSE`：用于流式返回生成答案和查询进度。
- `MCP`：通过 `MCPServerStreamableHttp` 调用外部 Web Search，作为本地知识库之外的补充检索。

### 模型与工具

- `BGE-M3`：生成 dense 和 sparse 两种向量，是 Milvus hybrid search 的基础。
- `FlagReranker`：用于对多路召回后的候选文档进行精排。
- `ChatOpenAI` 兼容接口：统一封装 LLM 调用，实际模型由环境变量配置。
- `MinerU`：将 PDF 解析为 Markdown。
- `LibreOffice soffice`：将 Word 文档转换为 PDF。

## 核心实现

### 知识入库流程

入库入口位于 `knowledge/api/import_router.py`，文件上传后由 `ImportFileService` 处理：

1. 生成 `task_id`。
2. 将上传文件保存到本地 `knowledge/temp_data/<date>/<task_id>/`。
3. 将原始文件上传到 MinIO。
4. 启动导入 LangGraph 流程。

导入流程定义在 `knowledge/processor/import_process/main_graph.py`，节点顺序如下：

1. `entry_node`：判断文件类型，识别 `md`、`pdf`、`doc/docx`。
2. `doc_to_pdf_node`：Word 文档通过 LibreOffice 转为 PDF。
3. `pdf_to_md_node`：PDF 通过 MinerU 转为 Markdown。
4. `md_img_node`：扫描 Markdown 图片，调用视觉模型生成图片摘要，并将图片上传到 MinIO。
5. `document_split_node`：基于 Markdown 标题和长度阈值生成 chunk。
6. `item_name_rec_node`：从文档内容中识别商品名，并回填到 chunk。
7. `bge_embedding_node`：对 chunk 批量生成 BGE-M3 dense/sparse 混合向量。
8. `import_milvus_node`：创建或重建 Milvus collection，将 chunk 写入向量库。
9. `kg_node`：调用 LLM 从 chunk 中抽取实体和关系，写入 Neo4j，并将实体名向量写入 Milvus。

最终形成的数据资产包括：

- 文档 chunk 向量集合：用于语义检索和关键词检索。
- 商品名向量集合：用于查询时商品名确认和对齐。
- 实体名向量集合：用于知识图谱检索前的实体对齐。
- Neo4j 图谱：用于查询实体关系和反查相关 chunk。
- MongoDB 会话历史：用于多轮对话上下文。
- MinIO 文件和图片对象：用于原始文件归档和图片资源访问。

### 查询问答流程

查询入口位于 `knowledge/api/query_router.py`，请求进入后由 `QueryService` 构造初始状态并调用 `query_app.invoke()`。

查询流程定义在 `knowledge/processor/query_process/main_graph.py`，核心节点如下：

1. `item_name_confirm`
   - 读取 MongoDB 历史会话。
   - 调用 LLM 从原始问题和历史上下文中提取商品名候选，并重写查询。
   - 使用 BGE-M3 将候选商品名向量化，在 Milvus 商品名集合中做 hybrid search。
   - 基于分数阈值将结果分为 `confirmed` 和 `options`。
   - 如果商品名明确，继续检索；如果不明确，直接返回候选反问或提示补充商品名。

2. 多路召回
   - `vector_search_node`：将重写查询向量化，在 Milvus chunk 集合中做混合检索。
   - `hyde_search_node`：调用 LLM 生成假设性文档，再向量化检索，缓解用户提问和文档表述不一致的问题。
   - `kg_search_node`：从问题中抽取实体，进行 Milvus 实体对齐，再查询 Neo4j 种子节点、一跳关系，并回填关联 chunk。
   - `mcp_search_node`：通过 MCP 调用外部 Web Search，提供本地知识库之外的补充信息。

3. `rrf_node`
   - 对向量检索、HyDE 检索和图谱检索结果做 RRF 融合。
   - 不直接比较不同检索源的原始分数，而是基于排名倒数累加，提升多路共同命中的文档。

4. `rerank_node`
   - 使用 `FlagReranker` 对 RRF 融合结果和 Web 搜索结果进行精排。
   - 通过动态断崖检测自动截断低相关文档，减少噪声进入最终 prompt。

5. `answer_output_node`
   - 整合精排文档、图谱关系、历史对话、商品名和用户问题。
   - 调用 LLM 生成最终答案。
   - 将用户问题和助手回答写入 MongoDB。
   - 流式模式下通过 SSE 推送 token 增量和最终答案。

## 核心业务逻辑

项目的核心业务逻辑可以概括为：

> 将商品资料加工成“向量库 + 知识图谱 + 对象存储”的知识底座，再通过“商品名确认 + 多路召回 + 融合精排 + LLM 生成”完成问答。

入库侧解决的是“资料如何结构化和可检索化”的问题。查询侧解决的是“用户问题如何准确定位商品、召回相关资料并生成答案”的问题。

系统特别重视商品名识别和对齐，因为商品名一旦误判，下游检索会围绕错误商品展开。项目采用 LLM 抽取候选、Milvus 向量对齐、阈值过滤、低置信度反问的组合策略，将误判尽量拦截在查询入口。

## 技术亮点

### 1. LangGraph 编排复杂流程

导入流程和查询流程都使用 LangGraph 建模。导入流程包含文件类型条件路由，查询流程包含商品名确认后的条件分支，以及四路检索的并行分发和汇合。相比线性 Chain，这种状态图更适合当前项目的复杂流程。

### 2. BGE-M3 混合向量检索

项目使用 BGE-M3 同时生成 `dense_vector` 和 `sparse_vector`。dense 向量负责语义相似，sparse 向量保留关键词匹配能力。Milvus 中通过 hybrid search 和 `WeightedRanker` 进行融合，适合商品型号、部件名称、操作步骤等场景。

### 3. 商品名确认机制

查询入口不是直接拿用户问题检索，而是先进行商品名确认。该机制结合：

- LLM 商品名抽取和问题重写。
- Milvus 商品名集合向量对齐。
- 高低阈值分段。
- 多候选分数差过滤。
- 不确定时主动反问。

这样可以减少商品名误判导致的错误检索。

### 4. 多路融合检索

项目并行使用四类召回方式：

- 标准向量检索。
- HyDE 增强检索。
- Neo4j 知识图谱检索。
- MCP Web 搜索。

本地多路结果通过 RRF 融合，再通过 Rerank 精排。该设计能缓解单一路径检索的漏召回问题。

### 5. HyDE 检索增强

HyDE 节点先让 LLM 生成假设性文档，再将“原问题 + 假设性文档”向量化检索。它适合用户问题短、口语化、和说明书表达不一致的情况。

### 6. 知识图谱增强

导入时从 chunk 中抽取实体和关系写入 Neo4j；查询时先抽取问题实体，再对齐实体名，查种子节点和一跳关系，最后反查关联 chunk。该流程让系统不仅能做语义相似检索，也能利用部件、步骤、条件、警告等结构化关系。

### 7. RRF 融合与动态断崖检测

RRF 避免直接比较不同检索源的原始分数，使用排名倒数累加提升多路共同命中的文档。Rerank 后的动态断崖检测通过相邻分数的绝对差和相对差动态决定保留多少上下文，减少低相关内容进入最终答案生成。

### 8. 面向文档结构的 chunk 切分

`document_split_node` 不是简单按固定长度切文本，而是先按 Markdown 标题切分章节，再对超长章节使用递归分隔符切分，对过短章节按同一父标题进行贪心合并。chunk 保留 `title`、`file_title`、`parent_title` 和 `part` 等元数据，便于后续检索和溯源。

## 解决了哪些痛点

### 1. 非结构化文档难以检索

PDF、Word、Markdown 等资料格式不统一。项目通过 MinerU、LibreOffice、Markdown 图片处理、文档切分和向量化，把非结构化资料转成可检索的 chunk。

### 2. 商品名和型号容易误判

用户提问常出现简称、口语表达或多商品混问。项目先用 LLM 提取候选，再通过 Milvus 中真实商品名集合进行对齐，降低误判扩散到下游检索的风险。

### 3. 单一向量检索容易漏召回

普通向量检索对短问题、术语错配、结构化关系问题不稳定。项目通过 HyDE、KG、Web 搜索补充召回，并用 RRF 和 Rerank 控制噪声。

### 4. 技术手册中关系型知识难以表达

说明书里常有部件、操作、步骤、注意事项、条件依赖。项目通过 Neo4j 存储实体关系，查询时可基于实体和一跳关系补充上下文。

### 5. 多轮对话上下文丢失

项目用 MongoDB 保存历史会话，并在商品名确认和答案生成时引入历史上下文，支持一定程度的上下文连续性。

### 6. 长文档上下文成本高

导入阶段做 chunk 切分，查询阶段做多路召回、RRF、Rerank 和动态截断，避免把大量无关内容直接塞给 LLM。

## 当前实现中的风险与不足

### 1. 组件数量较多，部署复杂度偏高

项目同时依赖 Milvus、Neo4j、MongoDB、MinIO、MinerU、LibreOffice、LLM API、BGE 模型和 Rerank 模型。架构能力完整，但环境搭建、运维和问题排查成本较高。

### 2. 外部 Web 搜索存在不确定性

MCP Web Search 作为补充召回合理，但会引入外部服务可用性、延迟和结果噪声问题。最终答案仍需要依赖 Rerank 和 prompt 约束降低噪声影响。

## 性能优化建议


### 1. 优化向量入库策略

当前 `ImportMilvusNode` 在确保 collection 时默认带有删除集合逻辑。实际生产场景建议按 `item_name` 或文档 ID 做增量删除和更新，避免每次导入重建整个集合。

### 5. 模型和数据库连接复用

项目中 BGE、Reranker、LLM、Milvus、Neo4j 已有部分单例缓存。建议进一步统一连接生命周期和失败重试策略，避免高并发下重复初始化模型或数据库客户端。

### 2. 控制图谱构建成本

`kg_graph_node` 会对 chunk 调用 LLM 抽取实体关系，并写入 Milvus 和 Neo4j。该阶段成本较高，建议：

- 对 chunk 做批量限流和重试。
- 缓存已处理文档的图谱结果。
- 对低价值 chunk 跳过图谱抽取。
- 记录失败 chunk，支持后续补偿处理。

### 7. 优化查询阶段延迟

查询阶段同时包含商品名确认、HyDE 生成、KG 检索、Web 搜索、Rerank 和答案生成。可优化方向：

- 对明确商品名查询减少不必要的 LLM 判断。
- Web 搜索设置超时和降级策略。
- 对 HyDE 检索设置开关，针对短问题或召回不足时再启用。
- Rerank 前限制候选数量，避免精排输入过多。

### 8. 增强可观测性

建议记录每次查询的关键指标：

- 商品名确认结果和分数。
- 各路召回数量。
- RRF 后候选数量。
- Rerank 截断位置。
- LLM 生成耗时。
- 最终使用的 chunk ID 和来源。

这些数据可以帮助评估召回质量、定位慢节点和分析回答错误原因。

## 总结

本项目围绕商品知识问答构建了一套较完整的 RAG 系统。其核心价值在于将文档解析、混合向量检索、商品名确认、知识图谱、多路融合、Rerank 精排和 LLM 生成组合成端到端链路。

从技术选型看，FastAPI 负责服务化，LangGraph 负责复杂流程编排，Milvus 负责混合向量检索，Neo4j 负责关系知识增强，MongoDB 负责历史会话，MinIO 负责对象存储。整体架构适合展示复杂 RAG 能力和多源知识增强能力。

当前系统的主要优化方向是提升工程稳定性、降低部署复杂度、完善 chunk 结构化切分、增强导入和查询阶段的可观测性，并对高成本节点引入缓存、超时和降级策略。
