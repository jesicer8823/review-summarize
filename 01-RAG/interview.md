# 项目总结文档

## 1. 项目定位

这是一个面向商品说明书、技术手册、产品资料的智能知识问答系统。系统的目标不是单纯做全文搜索，而是把非结构化文档加工成可检索、可融合、可追溯的知识底座，再通过多路召回与大模型生成，给出更稳定的问答结果。

整个系统可以概括为两条主链路：

- 知识入库链路：上传文档，解析、切分、识别商品、向量化、图谱化并写入存储。
- 查询问答链路：确认商品、并行多路检索、融合排序、生成答案，并支持流式输出。

---

## 2. 核心技术架构

### 2.1 服务与编排

系统使用轻量 Web 框架提供上传、查询、历史记录与流式响应能力。复杂流程采用状态图编排，而不是简单的线性调用链。这样可以自然表达：

- 条件分支
- 并行检索
- 节点汇合
- 状态在各节点间流转

这种架构特别适合“导入流程”和“多路召回流程”都比较复杂的场景。

### 2.2 多存储协同

系统不是只用一种数据库，而是按数据形态分工：

- 向量数据库：存储文本切片、商品名、实体名的向量表示，用于语义检索和关键词检索。
- 图数据库：存储实体关系，用于关系型知识增强。
- 文档型数据库：存储会话历史、多轮上下文和消息补全信息。
- 对象存储：存储原始文件和图片资源。

这种设计的优点是职责清晰，缺点是部署和运维成本更高。

### 2.3 模型分工

系统中的模型不是单一大模型包打天下，而是按角色拆分：

- 通用大模型：做商品名抽取、问题重写、HyDE 假设文档生成、实体抽取、最终答案生成。
- 向量模型：做 dense + sparse 双路表征，用于混合检索。
- 重排模型：对多路召回结果做统一精排。
- 视觉模型：为文档图片生成摘要文本。

---

## 3. 数据入库的核心逻辑

### 3.1 为什么统一成 Markdown

系统支持多种文档格式输入，但真正的统一中间表示是 Markdown。原因是：

- 结构化程度比纯文本高
- 更适合保留标题、段落、图片、表格信息
- 后续图片处理、文档切分、向量化都可以围绕它复用

因此，导入链路的本质是：先把不同输入格式尽快收敛到一个统一中间格式，再进行后续知识加工。

### 3.2 文档切分策略

文档切分不是简单按固定长度截断，而是一个“结构优先”的策略：

1. 先按 Markdown 标题切章节
2. 超长章节递归切分
3. 过短章节在结构允许的前提下合并
4. 保留章节级元数据，方便后续检索和答案溯源

这种设计解决了两个问题：

- chunk 太大时，检索不精确、上下文成本高
- chunk 太小时，语义不完整、召回碎片化

### 3.3 表格和图片为什么要特殊处理

表格需要做线性化处理，因为表格真正的语义在“字段-值”对应关系里，而不是单元格本身。直接把原始表格做向量化，往往会引入大量结构噪声，削弱语义。

图片也不能只作为二进制资源存在。系统会先为图片生成摘要，再把摘要和远程访问地址回写到文档中。这样图片语义就能进入文本检索链路，后续检索、重排和答案生成才能感知到图片内容。

### 3.4 图谱构建为什么要清洗

图谱构建前，对实体和关系做了较严格清洗：

- 实体名不能为空
- 实体名长度受限
- 实体标签必须在白名单中
- 同名同标签实体去重
- 悬空关系直接丢弃
- 不在白名单中的关系类型统一回退为弱语义关系

这套策略体现的是“高精度优先”。图数据库一旦写脏，比少写几条更难补救。

## 4. 查询问答的核心逻辑

### 4.1 为什么先确认商品名

系统在真正检索前，先做商品名确认，而不是直接拿用户问题去查库。这样做是因为商品名一旦识别错，后面的检索、重排、生成都会围绕错误商品展开。

商品确认采用的是两阶段策略：

1. 大模型先从问题和历史上下文中抽候选商品名，并重写问题
2. 再去向量库中做商品名对齐和分数过滤

结果会分成三类：

- 高置信：直接进入检索
- 中置信：返回候选给用户确认
- 低置信：提示用户补充更精确的商品名或型号

这种三级决策，本质上是用一次确认交互换取更低的误答风险。

### 4.2 为什么要带历史上下文

历史上下文不是为了“让回答更长”，而是为了处理真实对话中的指代问题，例如：

- 这个怎么用
- 那个怎么换
- 另一个型号呢
- 它支持什么

如果只看当前一句，商品名很容易丢失。系统还会在确认出商品名后，反向补全历史消息里的商品归属，提升后续轮次的消歧稳定性。

### 4.3 四路并行召回分别解决什么问题

系统使用四路并行召回，它们不是重复劳动，而是互补：

- 向量检索：解决正文语义相似问题，适合召回最直接相关的文本切片。
- HyDE 检索：解决用户口语化提问与文档正式表述之间的语义错位。
- 图谱检索：解决实体关系、步骤依赖、部件关联等结构化知识问题。
- Web 搜索：解决本地知识库之外的信息补充与兜底问题。

可以把它们概括为：

- 向量检索找“相似段落”
- HyDE 找“表达错位”
- 图谱检索找“关系证据”
- Web 搜索补“库外信息”

### 4.4 为什么 Web 结果不直接参与本地融合

本地三路检索最终都可以统一成内部文档切片，而 Web 搜索返回的是外部网页结果，两者不是同构对象，也没有统一主键和一致的分数语义。

因此，本地多路先做融合，再在重排阶段把 Web 结果作为补充候选统一比较相关性，这样更稳，也能避免外部噪声过早污染主检索链路。

## 5. 融合与重排策略

### 5.1 为什么用倒数排名融合

不同召回源的原始分数不可直接比较：

- 向量检索的分数有自己的范围
- 图谱检索的分数来自自定义权重
- Web 搜索未必有可比的原始分数

所以系统不直接融合原始分数，而是融合“排名位置”。这样可以提升多路共同命中的结果，同时避免某一路因为分数尺度大而主导最终排序。

### 5.2 为什么还要重排

多路召回只是把“可能相关”的候选尽量找回来，但最终上下文质量还需要统一裁决。重排模型的作用是：

- 在统一尺度上重新判断问题与文档的相关性
- 把不同来源的候选拉到同一个评价标准下
- 给最终提示词提供更干净的上下文

### 5.3 动态断崖检测的意义

重排后不是固定取前 N 条，而是根据相邻结果之间的分数断层，动态决定保留多少候选。这个策略的好处是：

- 问题简单时，减少噪声
- 问题复杂时，保留更多证据
- 避免固定 Top-K 在不同问题上过于僵化

同时设置保底下限，防止模型分数波动导致过早截断。

---

## 6. 为什么要用 dense + sparse 双向量

单一向量表示不够稳定：

- dense 擅长语义相似，但对型号、编号、专业术语的精确匹配不够敏感
- sparse 擅长关键词和词项匹配，但对口语化和改写表达不够鲁棒

所以系统同时使用：

- dense：解决“意思像不像”
- sparse：解决“词对不对”

二者结合做混合检索，更适合商品型号、参数、部件名称、说明书问答这类业务场景。

---

## 7. 流式输出的设计思路

系统支持流式返回答案，但流程编排仍然是状态图式的节点执行。这里的关键设计是把：

- 节点执行状态
- 大模型 token 增量
- SSE 响应通道

分离开处理。

最终实现效果是：

- 节点仍然返回完整状态
- token 增量走独立事件队列
- 服务端异步消费队列并按 SSE 协议推送给前端
- 同时还能推送节点级进度事件

这使得“流式回答”和“流程编排”可以并存，而不需要让状态图本身承担文本流传输职责。

## 8. 当前系统解决了哪些痛点

### 8.1 非结构化资料难用
把 PDF、Word、Markdown 等不同输入统一加工成可检索知识单元。

### 8.2 商品名歧义导致检索跑偏
通过商品名抽取、向量对齐、分层决策，把错误拦在查询入口。

### 8.3 单一路径检索容易漏召回
通过多路并行召回覆盖语义、关系、外部资料三个维度。

### 8.4 图文混合资料中的图片和表格难被利用
通过表格线性化和图片摘要，把结构化视觉信息转成可进入文本链路的语义内容。

### 8.5 多轮对话容易丢失商品上下文
通过历史消息参与商品确认和事后补全，增强连续追问的稳定性。

---

## 9. 当前最值得优先解决的三个问题

### 9.1 工程稳定性：导入一致性
当前导入链路对外部工具和多存储写入依赖较多，一旦中途失败，容易造成旧数据已删、新数据未完整写入的不一致状态。应优先解决导入版本切换、失败恢复和产物校验问题。

### 9.2 检索质量：chunk 结构还不够强
文档切分已经有比较好的基础，但标题层级、chunk overlap、图文关系和表格语义仍有提升空间。上游 chunk 质量会直接影响下游多路检索和答案生成上限。

### 9.3 用户体验：查询延迟波动较大
商品确认、HyDE、图谱检索、Web 搜索、重排、答案生成都可能触发外部调用。对明确商品名查询减少不必要的大模型判断，并给外部 Web 搜索加入超时与降级策略，会明显提升体感速度。

---

## 10. 性能与工程优化建议

### 10.1 导入侧
- 为导入引入文档版本号和生效切换机制，避免先删后写导致空窗期。
- 对文档解析结果做严格校验，避免“命令成功但产物无效”。
- 对图谱构建加限流、失败重试和失败记录机制。

### 10.2 检索侧
- 给商品名确认增加 fast path：明确型号时直接高置信对齐，减少一次大模型调用。
- 为 Web 搜索设置连接超时、调用超时和降级为空结果策略。
- 对本地召回不足时再启用外部搜索，减少外部依赖带来的抖动。
- 在重排前限制候选规模，降低精排成本。

### 10.3 可观测性
建议对每次查询记录以下指标：

- 商品名确认结果和分数
- 各路召回数量
- 图谱实体对齐数量
- 融合后候选数量
- 重排后保留数量
- 各节点耗时
- 大模型调用耗时
- 最终答案长度和来源分布

这些指标对于优化召回质量、分析延迟瓶颈、定位误答原因都非常重要。

---

## 11. 如果未来支持多租户

当前系统的隔离维度主要是商品名，未来如果支持多企业知识库，需要把租户标识升级成系统级隔离字段，并贯穿：

- 向量数据
- 图谱数据
- 会话历史
- 对象存储路径
- 查询过滤条件

商品名将不再承担系统级隔离职责，而只作为租户内的业务过滤条件。

---

## 12. 总结

这个项目的真正价值，不在于“接了多少组件”，而在于它把文档解析、文本切分、商品确认、多路召回、排序融合、图谱增强、流式输出这些能力，串成了一条完整的知识问答链路。

它不是一个简单的向量检索 Demo，而是一个具有较强工程思维的混合型 RAG 系统。  
当前架构已经具备较完整的能力面，下一阶段最值得投入的方向是：

- 提升导入一致性
- 提高 chunk 结构质量
- 降低查询时延波动
- 增强可观测性与可运维性

如果这些问题进一步解决，系统会从“可运行的复杂原型”更进一步走向“可持续优化的知识问答平台”。

## 13. 指标体系设计

从业务与技术两个视角看，这个项目都应该建立明确的指标体系。前者回答“系统有没有真正产生价值”，后者回答“系统为什么表现好或不好”。

### 13.1 业务指标

#### 首轮命中率

衡量用户第一轮提问后，系统是否就返回了可执行、可接受的答案。这个指标能直接反映商品名确认、多路召回和最终生成的整体协同效果。

#### 问题解决率

衡量用户问题最终是否被系统解决，而不是只返回了一段看似完整的文本。它比首轮命中率更宽，允许中间有一次澄清或补充。

#### 人工转接率

衡量系统最终仍需要人工介入的比例。这个指标直接反映项目是否真正降低了人工客服成本。

#### 用户满意度

可以通过点赞、评分、满意/不满意反馈等方式收集。它反映的是用户主观感受，通常比单纯的技术正确率更接近真实业务价值。

#### 多轮澄清率

统计多少请求在查询入口需要再次确认商品名、补充型号或补充问题。这个指标过高说明入口理解能力不足；过低也可能说明系统过于激进，容易误判。

#### 误答率

统计回答内容中商品识别错误、步骤错误、参数错误、事实错误的比例。这个指标决定系统风险边界，尤其适合技术说明书、操作指导类场景。

#### 知识命中率

衡量最终答案是否主要来源于企业自有知识库，而不是依赖外部搜索结果。这个指标能反映知识库建设价值和本地资料完备度。

#### 业务覆盖率

衡量已经支持的商品、文档、知识点范围。这个指标体现的是系统的可用边界，而不仅仅是单次回答质量。

### 13.2 技术指标

#### 商品名确认准确率

衡量商品名确认阶段是否把问题正确路由到了目标商品。由于商品名确认是整个检索链路的入口，这个指标通常要单独重点跟踪。

#### 商品名误判率

统计系统把问题错误映射到其他商品的比例。它和确认准确率相关，但更强调风险和错答代价。

#### Top-K Recall

衡量正确证据是否出现在召回结果前 K 条中。它是评估多路检索是否真的把有价值内容找回来的核心指标。

#### 排序质量指标

可以用 MRR、NDCG 等衡量正确证据是否排得靠前。这个指标比纯召回更进一步，直接对应后续生成阶段能否拿到高质量上下文。

#### Rerank 提升率

统计重排前后，正确证据排名提升了多少。这个指标能说明精排模型有没有真正带来价值。

#### 多路召回贡献度

分别统计向量检索、HyDE、图谱检索、Web 搜索各自提供了多少独有有效结果。这个指标适合回答“多路并行召回值不值得”。

#### 图谱检索命中率

衡量图谱检索是否真的补充了有效证据，而不只是增加了复杂度。

#### Web 依赖率

衡量最终答案有多少场景依赖外部 Web 搜索兜底。这能帮助判断本地知识库是否足够完备。

#### 答案正确率

衡量最终生成答案是否与资料事实一致，是最核心的生成质量指标。

#### 答案忠实度

衡量最终答案是否真正基于召回上下文，而不是模型自行发挥。这个指标可以反映幻觉控制能力。

### 13.3 性能与稳定性指标

#### 总响应时延

从用户发起查询到最终答案生成完成的总时间。它直接影响用户体感。

#### 首 token 时延

在流式场景下，用户第一次看到输出的时间。这个指标往往比总响应时延更影响交互体验。

#### 各节点耗时

分别统计商品名确认、HyDE、图谱检索、Web 搜索、Rerank、答案生成等阶段的耗时，用于定位瓶颈。

#### 导入成功率

衡量文档上传后最终成功入库的比例，是导入链路稳定性的基本指标。

#### 节点失败率

统计各节点发生异常的频率，适合发现 MinerU、LLM、Milvus、Neo4j、Web 搜索等外部依赖中的薄弱点。

#### 文档与索引质量指标

建议同时统计：

- 平均 chunk 数量
- 平均 chunk 长度
- 无效 chunk 比例
- 图谱实体数与关系数
- 图片摘要覆盖率

这些指标能帮助判断上游知识加工质量是否足够支撑后续检索。

### 13.4 推荐优先落地的核心指标

如果系统刚上线，不需要一口气把所有指标都做全。优先建议实现以下指标：

- 首轮命中率
- 问题解决率
- 人工转接率
- 用户满意度
- 商品名确认准确率
- Top-K Recall
- 答案正确率
- 总响应时延
- 首 token 时延
- 导入成功率
- 各节点耗时

这组指标已经能覆盖业务价值、检索质量、生成质量和系统性能四个核心维度。

### 13.5 推荐的指标分析视角

可以把查询链路看成一个漏斗：

```text
用户提问数
-> 商品名成功确认率
-> 本地召回命中率
-> Rerank 后有效证据率
-> 最终答案正确率
-> 用户满意率
```

如果漏斗某一层下降明显，就能快速定位问题究竟发生在：

- 商品确认
- 检索召回
- 排序过滤
- 还是最终生成阶段

### 13.6 指标落地建议

指标采集应尽量做成横切能力，而不是散落到每个业务节点里。推荐三层采集方式：

- 在节点统一入口采集节点级耗时、成功/失败状态
- 在外部依赖调用处采集 LLM、Milvus、Neo4j、Web 搜索耗时
- 在整条查询入口采集总链路指标

指标存储建议和业务数据分离，至少拆成两类：

- 查询聚合指标：记录一次查询的整体表现
- 节点明细指标：记录每个节点或每次外部调用的细粒度耗时与状态

这样后续做性能分析、召回评估、错误定位时会更高效。
