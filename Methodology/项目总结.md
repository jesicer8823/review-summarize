### 1. 提供清晰的上下文
1. AI 只能分析其看到的东西，总结前先明确项目边界
	* **角色定位** -> e.g:你现在是一名资深技术总监，请根据以下源码分析项目架构并撰写一份面向管理层的项目总结。
	* **输入关键文件**(防止 Token 溢出或重点偏移) -> e.g:summary --files "package.json, architecture.md, main.go
### 2. 使用结构化提示词(Structured Prompting)
模糊指令(如“总结这个项目”)通常只能得到浅显的描述，建议使用**模块化指令**

| 维度    | 可选的Prompt话语                     |
| ----- | ------------------------------- |
| 技术栈回顾 | 识别本项目使用的核心框架、数据库及中间件，并评价其选型的合理性 |
| 核心逻辑  | 追踪用户注册到数据入库的完整流程，用简练的语言概括核心业务逻辑 |
| 亮点与难点 | 分析代码中处理高并发或安全性的部分，总结其中的技术亮点     |
| 待改进点  | 基于代码规范和设计模式，指出当前项目中存在的过度设计或技术债  |


### 3. 递进式对话流
#### 1. 全景扫描
e.g：列出本项目的主要功能模块以及其依赖关系，项目结构等(添加限制条件，如src/目录下的源码)

#### 2. 深度挖掘
e.g: 针对 `API` 层的实现，总结其异常处理机制和日志记录策略；

#### 3. 格式化输出
e.g: 将以上所有分析整合成一份 `Markdown` 格式的报告，包含：概述、技术架构、核心实现、性能优化建议

### 4. 其他建议
#### 1. 优化技巧
 1.** 指定受众 **
	* 同样的内容，给开发者和产品经理看的内容是完全不同的(如给面试官讲解)
	* e.g 约束：1.对内：...强调 API 的扩展性和模块解耦方式；2.对外：...侧重于项目如何解决用户痛点和交付价值；
2. ** 约束长度与语气 **
	* e.g:...请使用专业、客观的语气，每个章节不超过 300 字，多用 Bullet Points
3. *** 自动提取指标 **
	* 如果你有日志或测试覆盖率报告，一并交给它
	* e.g:结合 coverage.out 的数据，总结测试覆盖情况并指出薄弱环节
#### 2. 坑点
* Token 限制：** 避免一次性塞入成百上千个源文件。优先传入 `README.md`、`API 定义`、`配置文件` 和 `核心逻辑入口`
* **幻觉校验：** Codex 偶尔会编造不存在的功能。在总结最后，可以加一句：`"如果代码中未体现某项功能，请明确标注‘未探测到相关实现’，不要虚构。"`

#### 总结
最好的交流方式是 **“背景 + 目标 + 限制条件 + 输出格式”**
e.g: 基于 `src/` 目录下的核心逻辑，写一份 500 字(可以不限制字数)的技术总结。目标读者是接手该项目的后继开发者，重点说明状态机的工作原理，并以 Markdown 列表形式输出。
